# 本地文章发布中心

> 交付时间：2026-11-02 23:10

一个只在本机运行的文章管理工具，用于创建、编辑、导入、预览、发布、归档与恢复博客文章。它不进入 Astro 生产路由，也不会部署到 Cloudflare Pages。

## 启动

要求 Node.js **>= 22.23.4**。在项目根目录执行：

```bash
npm install
npm run publisher
```

服务只绑定 `127.0.0.1`，默认地址：

```text
http://127.0.0.1:4322/
```

也可以直接双击项目根目录的 `PUBLISHER.command`。脚本会优先使用 Homebrew Node 24、启动服务并打开浏览器。

关闭方式：在终端按 **Ctrl+C**。关闭发布中心不会影响已经部署的线上博客。

## 创建第一篇文章

1. 点击“新建文章”。
2. 填写标题、摘要、分类和标签。
3. URL slug 会自动生成，也可以手动填写小写英文。**创建后不要修改 slug，否则会改变文章 URL。**
4. 点击“创建草稿并编辑”。

草稿写入 `src/content/blog/<slug>.md`，`draft: true`。草稿不会进入正式构建、RSS、Sitemap 或全文搜索。

## 编辑与保存

- 使用 CodeMirror 编辑 Markdown，右侧是实时预览。预览使用 Markdown-it 与站点全局 CSS；最终排版与 Content Collections Schema 以 Astro 生产构建为准。
- 输入停止约 1.2 秒后自动保存；`⌘S` / `Ctrl+S` 可立即保存。
- 保存使用同目录临时文件 + 原子替换，并在 `.publisher/backups/<slug>/` 保留最近 20 个版本。
- 点击编辑页的“恢复备份”可查看并恢复历史版本；恢复前会再备份当前内容。
- 编辑已发布文章时，“保存修改”会更新正文与 `updatedDate`，URL 和发布状态保持不变。

## 插入图片

- 点击工具栏“图片”，或在编辑器中粘贴/拖入图片。
- 图片写入 `src/assets/publisher/<slug>/`。
- 文件名会自动清理冲突字符；重名但内容不同会自动追加哈希后缀。
- 单张图片上限 15 MB，支持 PNG、JPEG、GIF、WebP、AVIF。
- 发布检查会验证正文引用图片是否存在。图片目录只会随当前文章一起暂存。

## 导入 Obsidian

支持：

- 选择 Obsidian Vault 文件夹或单篇 `.md` 文件；
- YAML frontmatter 的标题、摘要、分类、标签和日期；
- `[[文章名]]`、`[[文章名|别名]]`、`[[文章名#章节]]`；
- `![[图片.png]]`、带别名的图片嵌入和标准 Markdown 图片；
- 中文文件名、相对附件路径和附件重名。

流程：

1. 选择文件夹或 Markdown 文件，必要时补充图片附件。
2. 在下拉框明确选择要导入的**一篇**笔记。
3. 点击“分析并预览导入”。
4. 检查转换后的正文、目标文章、差异、标签映射和警告。
5. 确认“导入为本地草稿”。

安全边界：

- 不会自动扫描并发布整个 Vault；
- 只上传当前选中笔记的正文和正文实际引用的图片；
- 不确认不会覆盖已有文章；
- 同名标题或文件名会识别为**更新已有文章**，URL 保持不变；
- 无法解析的 Wikilink 会保留为文字并显示警告；
- 导入新文章始终是草稿；更新已发布文章保留原有发布状态。

## 发布流程

1. 在编辑页点击“发布检查”。
2. 发布中心会：
   - 校验必填字段、分类、标签、图片与站内链接；
   - 检查 slug 与文件状态；
   - 在实际生产构建前将文章标为正式文章；
   - 执行 `npm run build`（含 Astro 与 Pagefind）；
   - 展示文件清单与文本 diff；
   - 检查是否处于 `main`，是否存在其他未提交修改。
3. 检查通过后点击“确认发布到 main”。
4. 发布中心只暂存本次文章及 `src/assets/publisher/<slug>/`，创建提交并正常推送 `origin/main`。
5. 推送后会尝试核验线上文章的正文修订指纹（生产页面中不可见的 `article-revision` meta）。无法确认时明确显示“已推送，部署未确认”，并提供 Cloudflare 控制台入口。

发布记录保存在 `.publisher/history.json`，发布历史页面展示提交哈希、推送结果和可核验的部署状态。

## 归档与恢复

归档和恢复与发布共用同一套「检查 → 生产构建 → 文件差异 → 确认推送 → 线上核验」流程，不会只改本地文件。

**归档**（文章列表 → 行内「归档」）：

1. 进入「归档确认」页，页面显示标题、原 URL、分类标签、保留位置 `src/content/archive/<slug>.md`。
2. 输入**完整文章标题**后才能点击「运行归档检查」。
3. 检查会在本地把文件移到归档目录，并执行真实 `npm run build`；构建失败会自动移回，不产生任何提交。
4. 检查通过后可查看变更文件与文本差异。此时尚未提交；点「取消并还原」可恢复原状。
5. 点「确认归档并推送 main」后，发布中心只暂存这两个路径（`src/content/blog/<slug>.md` 删除、`src/content/archive/<slug>.md` 新增），创建 `post: archive <标题>` 提交并推送 `origin/main`。
6. 推送后核验线上 `/blog/<slug>/` 是否返回 404：返回 404 记为“已核验”，仍可访问则显示“已推送，部署未确认”。

归档前会扫描其他已发布文章，若仍存在指向该文的 `/blog/<slug>/` 链接，会在检查页给出警告（不阻断，但会留下死链，建议先改链接）。文章图片目录 `src/assets/publisher/<slug>/` 不随归档移动，恢复后可直接复用。

**恢复**（侧栏「归档与恢复」→「恢复」）：

1. 归档列表按归档时间倒序展示标题、归档文件路径、分类与冲突状态。
2. 点「恢复」进入「恢复确认」，检查会把文件移回 `src/content/blog/` 并沿用原 slug，因此**文章 URL 保持不变**。
3. 若博客中已存在同 slug 文章，检查直接拒绝（409），不会覆盖任何文件。
4. 恢复同样需要真实构建通过，之后确认推送；推送后核验线上页面正文指纹恢复正常。

归档与恢复都不提供批量操作，也不提供永久删除。历史记录会标注每条是“发布 / 归档 / 恢复”。

## 失败处理

- **内容校验失败**：按页面错误修改字段、标签或链接后重新检查。
- **Astro 构建失败**：构建日志保留在发布确认页；正文与草稿状态会恢复并保留，不会产生提交。归档/恢复的构建失败会自动把文件移回原位。
- **存在无关修改**：发布中心会拒绝提交，先单独处理这些文件。它绝不会把无关文件加入本次发布。
- **当前不在 main**：发布中心会阻止发布，不会自动切换、重置或强制推送。请安全合并并同步 `main` 后重试。
- **推送失败**：本地提交保留并写入历史，可修复网络或 GitHub 权限后手动重试；不会使用 `--force`。
- **部署未确认**：可点击“再次检查部署”，或打开 Cloudflare Dashboard → Workers & Pages 查看构建状态。

## 回退文章

- 编辑页“恢复备份”可回退到最近保存版本。
- 已提交内容可以通过 Git 历史查看。
- 误归档的文章在「归档与恢复」页点「恢复」即可，走完检查与推送后线上地址恢复；归档文件本身也保存在 `src/content/archive/`，不会被删除。

## 状态怎么看

界面上同时出现三类互不等价的状态，必须分开读：

| 位置 | 取值 | 真实含义 | 依据 |
| --- | --- | --- | --- |
| 状态列 | 草稿 / 正式文章 | 仅指 frontmatter 的 `draft` | 文章文件 |
| Git 列 | 未提交 / 本地修改 / 已提交 / 已推送 | 工作区与最后一次发布的推送结果 | `git status`、发布记录 |
| 发布历史 | 已推送，部署未确认 / 线上已核验 / 发布失败 | GitHub 与线上站点的实际结果 | 推送返回码、线上页面指纹 |

- **构建检查通过**只存在于本次检查记录中（默认 30 分钟内有效），不代表任何提交或部署。
- **已提交**不等于**已推送**，更不等于**已上线**；只有发布历史里的“线上已核验”才代表线上内容与本次发布一致。
- 无法确认时一律显示“已推送，部署未确认”，不会推断成功。

## 常见问题

- **检查时构建失败，日志里出现 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 或 `node-safe-delete-shim`**：说明启动发布中心的终端注入了沙箱删除拦截。发布中心已在构建子进程中自动剥离该 shim；如果仍然失败，用 `env -u NODE_OPTIONS npm run publisher` 重新启动。
- **提示“当前分支是 xxx，只允许从 main 发布”**：先在 Git 中安全合并并切换到 `main`，再重新检查；工具不会自动切换分支或重置提交。
- **提示“存在不属于本次发布的修改”**：先把与本次文章无关的改动单独提交或还原，发布中心不会把它们一起提交。
- **提示“本地 main 与 origin/main 不一致”**：先 `git fetch` 并安全同步，工具不会强制推送。

## 安全设计

- 服务固定监听 `127.0.0.1`，不监听公网地址；
- 校验 Host、Origin 和每次启动随机生成的 API Token；
- 本地页面不进入 Astro `src/pages`，生产站点不会暴露管理接口；
- API 没有任意命令执行能力，也不读取或输出 GitHub Token；
- 写文件只允许在 `src/content/blog`、`src/content/archive` 和 `src/assets/publisher` 内；
- 发布命令固定为项目 `npm run build`，Git 参数在服务端固定生成；
- Git 操作不提供强制推送、硬重置或删除历史。

## 测试

```bash
npm run test:publisher
```

使用临时目录和临时裸 Git 仓库验证，不会改动真实文章或推送 GitHub。覆盖新建、编辑、自动保存、版本冲突、备份恢复、Obsidian 中文与图片、重复导入、无效链接、构建失败、推送失败、无关修改拦截、发布差异、部署确认、归档与恢复（含构建失败自动还原、取消还原、同名冲突、线上 404 核验）、线上核验的四种结果、重复点击发布只产生一个提交、本机 API 鉴权和移动端布局。

生产构建与前台回归：

```bash
npm run check
npm run build
npm run test:smoke
```
